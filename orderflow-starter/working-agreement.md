# Working Agreement — Equipo OrderFlow

# Canales y tiempos de respuesta:

Las actualizaciones de código se realizarán por GitHub Desktop con su respectivo cambio documentado.
Cada actualización deberá incluir una breve descripción del cambio realizado, el motivo y el impacto esperado.
El canal principal de trabajo será la rama respectiva de cada desarrollador por feature o tarea.
Cada desarrollador deberá abrir un Pull Request para integrar nueva funcionalidad a la rama main.
El Pull Request tendrá un tiempo mínimo de revisión de 2 días.
Todo PR será revisado por los desarrolladores del equipo antes de ser aprobado.
No se realizará merge directo a main sin revisión previa y aprobación del equipo.

# Horarios de colaboración:

Los cambios y revisiones se permitirán únicamente en horarios hábiles de 9:00 a.m. a 5:00 p.m., de lunes a sábado.
Cuando exista una tarea crítica o bloqueo de producción, se podrá coordinar una excepción con el equipo.

# Criterio para pedir ayuda:

Cuando exista un bloqueo técnico, duda de implementación o riesgo de impacto, se deberá levantar un ticket en GitHub Issues para notificar a los responsables del proyecto.
El solicitante deberá:

- Presentar evidencia del problema a resolver
- Explicar el contexto y el impacto esperado
- Mostrar posibles soluciones pensadas y la opción recomendada
- Indicar el alcance del bloqueo y el nivel de urgencia
- Levantar el issue dentro del horario acordado en los lineamientos
- Esperar la respuesta del equipo antes de continuar con cambios de alto riesgo

# Responsabilidad sobre evidencias:

Todo cambio realizado debe tener evidencia clara de su ejecución y validación.
La evidencia puede incluir, según el caso:

- Capturas de pantalla
- Logs o resultados de pruebas
- Documentación técnica o de negocio
- Comentarios en el PR o en el issue relacionado
- Evidencia de validación funcional o de integración

Todo desarrollador es responsable de documentar:

- Qué se cambió
- Por qué se cambió
- Cómo se validó
- Qué riesgos o pendientes quedaron

# Regla para decisiones y desacuerdos:

Las decisiones del equipo deberán basarse en evidencia, impacto y prioridad del negocio.
Si hay desacuerdo, se debe:

- Revisar la evidencia disponible
- Analizar el impacto técnico y funcional
- Escuchar la opinión de todos los involucrados
- Escoger la solución con mayor beneficio y menor riesgo
- Registrar la decisión en la documentación o en el PR correspondiente

Cuando no exista una decision final deberá tomarse con base en:

1. La evidencia disponible
2. El impacto en el proyecto
3. La prioridad del objetivo a entregar
4. La experiencia y criterio del responsable de la decisión

En caso de conflicto, la decisión debe quedar documentada para evitar reabrir el mismo debate sin contexto.
